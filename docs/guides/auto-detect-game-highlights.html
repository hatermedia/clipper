How to automatically find highlights in gameplay footage

There are two honest ways to find a highlight: understand the game, or measure the signals players produce. Clipper takes the second path. It listens for sudden loudness, watches for sudden motion, and cuts where both agree. No upload, no model download, no cloud bill.

Why not just use an AI model?

Semantic models can be genuinely useful. They can recognize a boss health bar, a kill feed, or a victory screen. They also add a model download, GPU or API cost, latency, and a new failure mode when the model misreads a game it has never seen.

For the “I have 40GB of clips and want the loud/fast parts” problem, signal processing is a better first pass. It is fast, deterministic, private, and works on any game. You can still send the shortlist to a semantic model later if you want.

The audio track: short-time RMS vs. a rolling baseline

Clipper extracts mono 16kHz PCM with FFmpeg and computes RMS in 50ms windows. Raw loudness is not enough: a constant-loud gunfight and a quiet video with one yell are different. The useful signal is contrast.

  1. Compute RMS for each window.
  2. Build a 4-second rolling median as the “normal” loudness of this footage.
  3. Measure how far each window exceeds that baseline.
  4. Convert the excess to a robust z-score; blend in absolute loudness.
  5. Smooth and normalize to the 99th percentile.

A 0.5-second reaction in a quiet stretch scores high. A continuous loud section gets less credit for simply being loud, which is what you want.

The visual track: a tiny proxy and frame deltas

Reading every frame of a 4K60 video with OpenCV is wasteful. Clipper asks FFmpeg for a 320px-wide, 4fps proxy, then reads that with OpenCV. For each frame it computes:

  • Mean absolute difference from the previous frame: camera flicks, explosions, fast movement.
  • 90th-percentile difference: small bright changes such as a kill-feed flash or hit marker.
  • Whole-frame brightness change: flashes and fades.

The raw values are normalized with a p95 scale plus a percentile rank. That keeps sustained motion visible without letting one hard cut flatten everything else.

Fusion: one score, adaptive threshold

Both tracks are resampled onto a 0.25-second grid and blended. The default is 60% audio, 40% motion, with a small bonus when both detectors agree. The combined score is smoothed, then peaks are selected with a threshold derived from your sensitivity setting.

A lower sensitivity uses a more extreme percentile (fewer clips). A higher sensitivity lowers the bar. Peaks must be at least four seconds apart, which avoids six overlapping clips of the same explosion.

Padding and merging

Each peak becomes a window: by default, 8 seconds before and 5 seconds after. Overlapping or near-overlapping windows merge. A 25-second team fight stays one clip, not five fragments with cuts in the middle.

Then Clipper clamps to the video duration, drops clips under the minimum length, caps the count, and sorts chronologically.

What it will miss

Heuristics do not understand context. A loud menu sound can score. A quiet clutch can be missed. A dramatic pause can be more important than the explosion after it. That is why Clipper has a dry-run mode with preview frames: review the shortlist before you render.

If you need semantic understanding, use this as a fast first pass, then review the clips or run a second model on the shortlist. Do not pretend a frame-difference score is game understanding.

FAQ

Is this machine learning?

No. It is signal processing: RMS, median filters, robust z-scores, frame differencing, percentile normalization, and peak picking. That is a feature for privacy and predictability, not a limitation to hide.

Does it need a GPU?

No. Analysis uses a small proxy and CPU OpenCV. NVENC is optional for faster re-encoding.

Can I use it on a 4-hour VOD?

Yes, but expect it to take longer. The proxy keeps memory use low; the decode pass is the cost.

Does it upload anything?

No. Everything runs locally, and the web UI binds to 127.0.0.1 by default.
