Lossless vs re-encode: how to trim gameplay clips without quality loss

A “lossless” clip does not mean the file size stays the same or that the cut is magic. It means FFmpeg copies the compressed video and audio streams without decoding and re-encoding them. That has one big benefit and one sharp trade-off.

What stream copy actually does

H.264, HEVC, and AV1 video are made of keyframes and predicted frames. A keyframe is a full picture; the frames after it describe only what changed. You cannot start decoding a predicted frame without the keyframe it depends on.

When you run:

ffmpeg -ss 13.75 -i input.mp4 -t 4 -map 0:v:0 -map 0:a:0? -c copy output.mp4

FFmpeg seeks to the nearest keyframe at or before 13.75 seconds and starts copying there. The output is not re-encoded, so quality is untouched and the export is nearly instant. But the clip may start earlier than you asked.

The keyframe trade-off

On a typical 30fps recording with a 2-second keyframe interval, the previous keyframe can be up to two seconds early. On a long-GOP capture it can be worse. For a highlight, a little extra run-up is usually good: you see the approach, not just the explosion.

For a tight montage, it is not good. A clip that starts two seconds early can overlap the previous clip or include a menu. That is when you re-encode.

Rule of thumb: use stream copy for a fast review pass and most social clips. Use re-encode when every frame of the in/out point matters, or when the source container/codec cannot be copied into the target container.

When to re-encode

  • You need exact in/out points for a montage or beat sync.
  • The clip starts on a menu, loading screen, or previous scene.
  • The source is 10-bit/HDR and you need a shareable SDR H.264 file.
  • Stream copy fails because the codec is incompatible with the output container.
  • You need a smaller file and can accept a quality/size trade-off.

Frame-accurate cuts with Clipper

clipper --input "D:\Captures" --output "D:\Highlights" --reencode --encoder libx264 --crf 20

Or with an NVIDIA GPU:

clipper --input "D:\Captures" --output "D:\Highlights" --reencode --encoder h264_nvenc

Re-encoded output is H.264/HEVC + AAC in an MP4. If the GPU encoder is listed but unusable, Clipper retries with libx264. Re-encoding is slower, but the edges are exact and the file is broadly compatible.

Quality, size, and generations

Every re-encode is a new generation of compression. At a reasonable CRF (18–23 for x264), one generation is usually invisible on gameplay. Repeatedly re-encoding the same clip will eventually soften particles, text, and fine HUD details.

Stream copy avoids generations entirely. If you plan to edit the clip again in Premiere, Resolve, or CapCut, keep the lossless version as your source and export the final delivery from that.

Why the clip says 4 seconds but the file is 4.1

Container timestamps and keyframe alignment can add a frame or two. Compare the actual content, not only the duration metadata. If a clip starts noticeably early, that is keyframe alignment, not a bug.

Try both on one clip

Export the same window with and without --reencode. Compare the first second and the file size. That will tell you more than any benchmark.

FAQ

Is stream copy really lossless?

Yes, for the streams being copied. The video/audio bitstreams are not re-encoded. The container is rewritten, and metadata may change.

Can I stream-copy into any container?

No. Codec/container compatibility matters. Clipper retries with H.264/AAC when a copy fails.

Does re-encoding always reduce quality?

It is a new lossy generation. At a good CRF the difference is usually invisible, but repeated generations add up.

Which is faster?

Stream copy is effectively disk-speed. Re-encode is CPU/GPU-bound; NVENC is much faster than libx264 when it works.
